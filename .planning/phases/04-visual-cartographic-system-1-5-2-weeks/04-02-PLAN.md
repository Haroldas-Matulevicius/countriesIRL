<objective>
Build the ramp data model as a pure, `node`-testable module: a ramp is a hue family plus **N ordered
shades**, with `shadeForIndex(i, n)` and `shadeForValue(t)` accessors and a serialization-stable id.

Purpose: **D4-01 is deliberately first because everything downstream binds to it.** The legend's row
count, `04-07`'s WCAG contrast gate, `04-05`'s `{rampId, t}` identity, and Phase 5's classing engine
all derive from a *bounded* step set. Owner framing, recorded verbatim in `04-CONTEXT.md` D4-03
because it is the constraint this module must satisfy: *"the shades will later also be based on
country statistics, like if Poland is 100% for something and Lithuania gets entered as 50% for
something, it needs to understand that Lithuanias shade is half of what polands should be, so later
it has to be connected to data."* That is **proportional shading against a normalized position**,
which is exactly `shadeForValue(t)`.

Output: `src/utils/ramps.ts` and a unit suite whose every assertion has been observed RED on its own
subject.
</objective>

<stated_assumptions>
- **U-1 — step count `N = 5`, uniform across all ramps.** `[ASSUMED — Claude's discretion per
  `04-CONTEXT.md`; the number is derived, not chosen.]` Panel content width at 360px is
  360 - 2 x 16 = **328px**; a strip segment must remain a legitimate target, so `328 / N >= 44`
  gives `N <= 7` (`328/7 = 46.9` passes, `328/8 = 41` fails). `N = 5` gives 65.6px segments,
  headroom if the panel ever narrows, and a bounded `5 ramps x 5 shades = 25`-assertion contrast
  gate. **Uniform N is deliberate**: a per-ramp N would make strip geometry, legend row count, and
  gate arity vary per ramp for no product gain. Cost to reverse: low now, **costly later** — D4-01
  says the legend, the contrast gate, and Phase 5's classing engine all bind to the step set.
- **U-2 — families `Blues`, `Reds`, `Greens`, `Purples`, `Greys`.** The roadmap's own stated set plus
  a neutral. Exact hexes are plan-time work under the binding gates below; the constraints, not the
  hues, are what is load-bearing.
- **U-12 — shade sets are globally disjoint.** `04-RESEARCH.md` Open Question 5 asks whether to
  guarantee disjointness or re-key legend entries off `{rampId, index}`. `04-UI-SPEC.md § 6.3.4`
  closes it in favour of **disjointness**, because re-keying legend entries is a storage change for a
  problem a palette choice avoids. Recorded as a spec decision, not an owner decision.
- **Adjacent-step contrast is NOT gated at 3:1.** `04-RESEARCH.md` records `[ASSUMED, A2]` that a
  5-step sequential ramp cannot hold 3:1 between every neighbour inside sRGB for most hues. A gate
  that is **red on arrival gets loosened rather than obeyed**. Distinguishability is the legend's
  job, not the ramp's. Adjacent separation is therefore **measured and recorded**, not thresholded.
  If the measurement shows 3:1 is in fact achievable for every shipped ramp, say so and propose the
  stricter gate in the SUMMARY rather than adding it silently.
</stated_assumptions>

**Gate 1 — monotone luminance.** For each ramp, map shades through `relativeLuminance(parseHexColor(hex))`
and assert each step is strictly less than its predecessor, with a per-step message naming the ramp
id and the step index. Assert the mapped array length against the ramp's `shades.length`, so the loop
cannot pass vacuously. Do **not** write the roadmap's "shuffle a ramp" form as the only subject — a
two-element shuffle is the identity half the time, so it can be green by accident.

**Gate 2 — global disjointness.** Collect every shade from every ramp into one array, and assert the
`Set` of them has size equal to `RAMPS.length * RAMP_STEP_COUNT` written as the **literal 25**, not as
a product of two `.length` reads. Add a message naming which hex collides. This is what prevents
`normalizeLegendEntries` from silently collapsing two ramps' legend entries.

**Gate 3 — label contrast.** For every shade assert
`max(contrastRatio(shade,'#FFFFFF'), contrastRatio(shade,'#111827')) >= WCAG_AA_BODY_RATIO`, with a
message naming the shade and both measured ratios. This is exactly the automatic light/dark label
selection the ramp strip's check glyph will perform, so the gate asserts the renderer's real choice
rather than a hypothetical one. Assert the assertion count against the literal 25.

**Adjacent-step separation is a measurement, not a gate.** Compute `contrastRatio` between each
adjacent pair, log the full table, and record the **minimum observed value** in the SUMMARY. Do not
add a threshold. If every shipped ramp turns out to clear 3:1 between neighbours, say so and propose
the stricter gate in the SUMMARY as a follow-up — do not add it in this plan.

**RED-proof each of the three gates, on its own subject. This is a required step with its own
acceptance criterion, not a hope.** For each gate in turn: copy `src/utils/ramps.ts` to the
