### 0.4 The one rule that governs every visual decision below

> **What the creator sees inside the export frame and what lands in the PNG are the same thing.**

A serialised SVG rasterised as an `<img>` is an **isolated document**. Measured in installed
Chrome this session: a host-stylesheet **class rule** renders as SVG's default black, and a `var()`
pointing at a host `:root` token renders as **nothing at all**
(`04-RESEARCH.md § Export Fidelity Envelope`). Therefore:

- Anything that must appear in the PNG is an **inline attribute or an inline style inside the
  serialised subtree**. Never a class, never a host `var()`, never `filter` / `backdrop-filter`.
- `--map-surface` contributes **zero pixels** to the PNG today. Water becomes a serialized `<rect>`.
- Editor-only affordances carry `data-editor-only`, which `sanitizeExportClone` strips wholesale.
  That attribute is the **guarantee** an affordance cannot move exported pixels.

### 1.1 Why the typography rules SURVIVE the widening (the non-obvious half)

The near-size adjacency rule and the `--text-subheading` ban are stated *as if* they are about
column width, but their actual subject is **a 2px size difference reading as an accident rather
than a hierarchy**. A 2px step is just as illegible at 360px as at 280px — the width was the
occasion, not the cause. **Both rules stay in force at 360px, with the reason restated as
"within any tool panel" rather than "within the 280px column."**

This matters because a careless renumber would have read those rules as satisfied by the widening
and reintroduced 16px sub-headings into the panel — exactly the drift the annotation exists to
prevent.

### 1.2 What the widening actually BUYS — the one rule that relaxes

`:718` / `:798` claim a full-phrase control row "has no width at which it fits a 280px column."
At 360px minus 2 × 16px padding = **328px** of content width, that claim is measurably false for
short pairs.

**Replacement rule (this spec):** a control row may hold **at most two** full-phrase controls, and
only when the sum of their labels is **≤ 24 characters**, derived at `--text-body-sm` (14px) with
Inter's worst-case advance width 1.0202em → 14.28px/char → 24 chars ≈ **343px of glyphs alone**
(24 × 14.28 = 342.8). Adding a `--space-sm` (8px) gap and two `--space-md` (16px) paddings brings the
row to **≈ 383px** (342.8 + 8 + 32 = 382.8)… which **exceeds 328px** by a wide margin. So:

> **Measured outcome: even at 360px, two full-phrase controls do not fit on one row.**
> `:718` and `:798`'s *practice* is preserved and their *stated reason* is corrected: the
> constraint is Inter's advance width against 328px of content, not the number 280.

Icon-only rows, single-word pill groups, and a label + a single short control **do** fit and are
the intended use of the extra 80px. This is recorded so nobody "discovers" the extra width later
and puts a `Reset All Colors` / `Apply Color` pair on one line.

### 1.3 A number collision to state out loud

`editor.css:129` already declares `--panel-height: min(60dvh, 360px)` for the **compact bottom
sheet**, and `editor.css:157/183` discuss **360px** as the narrowest contained viewport. After
D4-05, `360px` means three different things in one stylesheet. **The open flyout width must be
declared as a named token, never as a bare literal**, so a future reader cannot conflate them:

```css
:root { --panel-width-open: 360px; }                              /* NEW, editor.css */
.map-editor[data-panel-open='true'] { --panel-width: var(--panel-width-open); }
.tool-panel__body { width: var(--panel-width-open); }             /* replaces the literal at :616 */
.map-workspace > .editor-help { max-inline-size: var(--panel-width-open); } /* replaces :783 */
```

`editor.css:783`'s literal `280px` is documented as *"capped at the panel's own measure"* — it is a
**derived** value and must become a `var()` rather than a second literal, or it will drift the next
time the panel moves. `--panel-width-open` lives in `editor.css`, not `theme.css`, so the
`themeTokens.test.ts` namespace allowlist does not apply to it (that allowlist governs `theme.css`
only). **Do not add it to `theme.css`.**

Unchanged from `Design.md § 5`. Restated for the checker.

| Token | Value | Usage |
|---|---|---|
| `--space-xs` | 4px | icon gaps, inline padding, swatch gutters |
| `--space-sm` | 8px | compact element spacing, grid gaps inside the panel |
| `--space-md` | 16px | default element spacing, **panel horizontal padding** |
| `--space-lg` | 24px | section padding, floating-control inset from the canvas edge |
| `--space-xl` | 32px | gap between panel sections |
| `--space-2xl` | 48px | **minimum interactive control height** |
| `--space-3xl` | 64px | HUD header block height |
| `--target-compact` | 44px | touch target under the narrow breakpoint (D-20) |

**Exceptions: none.** Every Phase 4 dimension is a multiple of 4: panel **360**, rail 56, rail row
36, rail icon slot 32, icon glyph 20, control min-height 48, touch target 44, ramp strip height 48.

**Composition-layer geometry is a separate scale** and is *not* spacing tokens — it is in **user
units of the 1080 viewBox**, written as inline SVG attributes. Every value here is **derived, not
chosen** — but note that the chrome scale's multiples-of-4 rule **does not apply to this table** and
is not claimed for it. This is a viewBox user-unit scale whose values fall out of divisions of 1080;
`BAND_MAX_HEIGHT` (154) and the subtitle steps (22, 26) are not multiples of 4 and do not need to be.
The chrome spacing scale above remains multiples-of-4 and exception-free.

| Constant | Value | Derivation |
|---|---|---|
| `MAP_VIEWBOX_SIZE` | 1080 | existing (`src/constants/config.ts`) |
| `LEGEND_SAFE_INSET` | 32 | existing (`legend.ts:13-24`) |
| `BAND_MAX_HEIGHT` | **154** | `Math.floor(MAP_VIEWBOX_SIZE / 7)` — the roadmap's 1/7 cap. **Write the derivation, not the literal**; 1080/7 = 154.28… is not an integer and a plan that says "1/7" beside a test that says "154" will disagree the first time the viewBox moves |
| `BAND_DEFAULT_HEIGHT` | **120** | `MAP_VIEWBOX_SIZE / 9` — exact integer, ~78 % of the cap, tall enough for a title at size L (56) plus a subtitle at size M (26) with `LEGEND_SAFE_INSET` breathing room |
| `TEXT_SAFE_INSET` | 32 | `= LEGEND_SAFE_INSET`. **One inset for every composition edge**, so title, legend, and attribution align on the same left rule — this is what makes the reference read "well structured out" |

## 4. Typography

### 4.1 Chrome type (rail, panels, HUD) — unchanged

The panel uses exactly the four chrome roles Phase 3 declared, at 360px as at 280px (§ 1.1):

| Role | Size | Line height | Weight | Phase 4 consumers |
|---|---|---|---|---|
| `--text-h3` | 18px | 1.40 | 600 | tool panel title (`Colors`, `Map style`) — **one per panel, never repeated inside it** |
| `--text-body-sm` | 14px | 1.50 | 400 | rail rows, option pills, inputs, list rows, ramp names. **At weight 500** for panel section labels |
| `--text-caption` | 12px | 1.40 | 400 | helper text, hex values, field errors, step labels, character counters |
| `--text-eyebrow` | 11px | 1.30 | 500 | inert pills only |

**`--text-subheading` (16px) does not appear in a tool panel at any width** (§ 1.1). **Panel section
labels are `--text-body-sm` at weight 500** — hierarchy inside the panel is carried by weight, never
by a 1–2px size step.

### 4.2 Composition type (inside the exported PNG) — NEW

All sizes are **user units of the 1080 viewBox**, all weights are Inter, all ink is
`--map-fixed-text` (`#111827`) written as an **inline `fill` attribute**, never a class or a `var()`.

| Element | Size steps (user units) | Weight | Anchor | Notes |
|---|---|---|---|---|
| **Title** | S 36 · **M 44** · L 56 | 600 | `text-anchor` = start/middle/end, creator-chosen; default **start** | Sits in the top band |
| **Subtitle** | S 22 · **M 26** · L 32 | 400 | inherits the title's alignment | Optional; parenthetical in the reference |
| **Attribution** | fixed **20** | 400 | start (bottom-left) or end (bottom-right) | No size step — it is meta, and a size control on meta is a control nobody uses |
| **Legend caption** | 24 | **600** | start | One bold line above the marks (the reference's `EU = 6.0%…`) |
| **Legend label** | small 24 · **medium 32** · large 40 | 600 | start | **Unchanged** from `LegendOverlay.tsx:34-38` + D-25 |

#### There is exactly ONE map ink, and the reason is arithmetic

The Eurostat reference sets attribution in **small grey type**. **This spec deliberately does not
copy that**, and the reason is measured rather than aesthetic:

- A second fixed ink (say `#4B5563`) has relative luminance **0.0889**.
- For it to clear WCAG AA 4.5:1 against a creator-chosen water surface of luminance `L`:
  `(L + 0.05) / (0.0889 + 0.05) ≥ 4.5` → **`L ≥ 0.575`** — i.e. only near-white water would be legal.
- `--map-fixed-text` `#111827` has luminance **0.0091**, giving **`L ≥ 0.216`** — every surface
  lighter than mid-grey `#808080` (L = 0.2159) is legal.

**A second ink would silently constrain the water palette to near-white and make OQ-1 unanswerable.**
Hierarchy in the composition is therefore carried by **size and weight only** — the same discipline
`Design.md` already applies inside the tool panel. Attribution reads as secondary because it is 20
units at weight 400 in a corner, not because it is grey.

> **Consequence, stated as a gate:** every shipped water/background preset must have relative
> luminance **≥ 0.216** (lighter than `#808080`). This is a `node`-testable pure assertion over the
> preset table, RED-provable by adding a navy preset. It **bounds** Open Question 1 without closing
> it.

#### Character bounds — no DOM, so bounds are character counts

Vitest runs in `node`. Text measurement is impossible. Reuse the exact derivation
`LEGEND_CHARACTERS_PER_LINE` already records (`legend.ts:69-92`): *the widest common character is
`W` at **1.0202em***. Available width = `1080 − 2 × TEXT_SAFE_INSET` = **1016 user units**.

| Element | Size | `floor(1016 / (size × 1.0202))` | Bound |
|---|---|---|---|
| Title | S 36 | 27.6 | **27** |
| Title | M 44 | 22.6 | **22** |
| Title | L 56 | 17.8 | **17** |
| Subtitle | S 22 | 45.3 | **45** |
| Subtitle | M 26 | 38.3 | **38** |
| Subtitle | L 32 | 31.1 | **31** |
| Attribution | 20 | 49.8 | **49** |

**Do not invent a different bound and do not re-measure casually.** If the executor re-measures in
Chrome, the new number and its method go in the same commit, and `LEGEND_CHARACTERS_PER_LINE` moves
with it — `04-07` and `04-08` both derive from the same measurement, and whoever moves one moves
both (`04-RESEARCH.md § Text Tools`, the `F-1` interaction).

**Refusal, not truncation.** Exceeding a bound blocks `Export PNG` with a creator-facing message
(§ 9), mirroring `getLegendBlockingMessage`. It is decided **synchronously**, is unfixable by retry,
and is never offered one.

## 5. Color

### 5.1 Chrome — the 60/30/10 split (inherited, unchanged)

| Role | Token | Value (light / dark) | Usage |
|---|---|---|---|
| **Dominant (60 %)** | `--themely-platinum` | `#ffffff` / `#000000` | Editor wall, **tool panel body**, tile surfaces |
| **Secondary (30 %)** | `--themely-porcelain` | `#f8fafd` / `#16181c` | Rows, hover surfaces, inset zones |
| **Active surface** | `--themely-powder` | `#e5edf5` / `#1d1f23` | The open tool's rail row; the selected pill, tile, or ramp step |
| **Accent (10 %)** | `--accent-fill` | `#0071e3` **both modes** | See the reserved-for list below |
| **Destructive** | `--destructive` | `#b42318` / `var(--themely-red)` | `Delete Saved Map`, error edges. Never decorative |

**Accent is reserved for, and ONLY for:**

1. The rail footer's **`Export PNG`** filled button (`--accent-fill`).
2. The **one** primary action of a panel that has one — in Phase 4 that is `Apply Color` in the
   Colors panel and `Save Map` in the Saved Maps panel.
3. `:focus-visible` rings, globally — the one documented exemption from the per-surface budget.

**The `Map style` panel has NO primary action and therefore carries NO Apple Blue at all** (D-05).
Its selected states are Powder + Midnight Ink. This is not an oversight; it is the rule.

### 5.2 Composition color — NEW, and it is not a token system

Everything a creator can change about the map's appearance becomes **persisted composition state**
serialized as inline SVG attributes. **None of it is a CSS token**, because a token cannot reach the
export clone.

| Composition property | Storage | Rendered as | Default |
|---|---|---|---|
| Water / background | `settings.surfaceColor` | `<rect data-layer="surface" x=0 y=0 width=1080 height=1080 fill="…">` | `#FFFFFF` (D4-16 / owner reference) |
| Uncolored country fill | `settings.uncoloredFill` | inline `fill` per path, resolved by `getEffectiveFeatureColor` | **`#E5E7EB`** — reuses `NEUTRAL_UNIT_COLOR` verbatim (D4-09) |
| Border color | `settings.borderColor` | inline `stroke` | `#000000` (`DEFAULT_BORDER_COLOR`, unchanged) |
| Interior border weight | `settings.interiorWeight` | inline `stroke-width` on the mesh | `thin` (0.75) |
| Coastline weight | `settings.coastlineWeight` | inline `stroke-width` on country paths | **`none` (0)** — see § 6.4 |
| Band color | derived from `settings.surfaceColor` | `<stop stop-color="…">` **inline literal** | derived (D4-16) |
| Composition ink | **not creator-facing** | `--map-fixed-text` `#111827` written inline | fixed |

**`#FFFFFF` remains the stored sentinel for "not colored"** (D4-09). Only the *render* maps it to
`settings.uncoloredFill`. Storage, legend exclusion, and undo-history semantics are untouched. This
is the same render-time-mapping pattern `getEffectiveFeatureColor` already applies to null-owner
units — it is a reuse, not a new mechanism.

**`NEUTRAL_UNIT_COLOR` is freed, not deleted.** D4-10 removes the "not colorable" bucket entirely
(all twelve neutral units become colorable), so the constant's original meaning dissolves and its
value `#E5E7EB` becomes the default meaning of *uncolored*. There is no grey-vs-grey ambiguity left
to design around.

### 5.3 The export firewall still governs, and it got wider

Every token in `Design.md § 3`'s mode-invariant set is declared **exactly once, in the unconditioned
`:root`**, and appears in **no** `.dark` block, no media query, no `@supports`. Phase 4 adds nothing
to that set and **must not**.

But note what actually changed: the tokens in that table were the export firewall *because* they
were believed to paint exported pixels. Measurement says `--map-surface` paints **zero**. The
firewall's real teeth in Phase 4 are the **serialized inline attributes**, and the token set's job
narrows to the editor's own chrome and the skeleton/loading state.

> **Do not "simplify" `--map-surface` away.** It still paints the letterbox gutter and the loading
> skeleton, and deleting it would leave the gutter unpainted. Its § 3 row should gain an annotation:
> *"paints the editor gutter and skeleton; contributes zero pixels to the PNG — the exported square's
> colour comes from `[data-layer=surface]`."*

**Gutter vs. square** `[ASSUMED — owner did not decide]`: the surface rect paints the **1080 square
only**; the letterbox gutter outside it keeps `--map-surface` (mode-invariant `#ffffff`), and
`--map-frame-scrim` keeps dimming it. Rationale: the frame's whole job is to show what survives the
crop, and a visible tint boundary at the frame edge *reinforces* that rather than fighting it.

**Contract for Phase 4** `[ASSUMED — owner did not decide; OQ-2 stays OPEN]`:

> **Say this out loud in the plan:** Phase 5's roadmap entry `05-05` names a "Data HUD section" —

#### 6.3.4 The ramp strip — the component that carries the phase

The strip must **visually rhyme with the exported legend bar**. Same idiom, one in chrome tokens

like a colour picker.

| Part | Contract |
|---|---|
| Container | **One** contiguous horizontal band. `--radius-control` (8px) on the **outer** corners only, `overflow: hidden`, `border: var(--border-width) solid var(--swatch-border)` on **the band**, not per segment. Height **48px** (`--space-2xl`, the interactive floor) |

| Selected | A `check` glyph (16px) centred on the segment, drawn in **whichever of `#FFFFFF` / `#111827` clears 4.5:1 against that shade** — the same automatic light/dark selection the contrast gate asserts. **Never a Powder background**, which would hide the shade being selected. Plus a 2px `--accent-fill` inset ring? **No** — the accent budget is spent on `Apply Color`; the ring is `--themely-midnight-ink` at 2px inset |

**Step count is 5, and the number is derived, not chosen** `[ASSUMED — Claude's discretion per
CONTEXT]`:

- Content width at 360px = **328px**. A segment must remain a legitimate target: `328 / N ≥ 44`
  → **N ≤ 7**. (`328/7 = 46.9` ✓; `328/8 = 41` ✗.)
- `N = 5` gives **65.6px** per segment — comfortably above the floor, leaves headroom if the panel
  ever narrows, and keeps the WCAG label-contrast gate to a bounded `5 ramps × 5 shades = 25`
  assertions.
- **All Phase 4 ramps carry exactly 5 shades.** Uniform N is deliberate: a per-ramp N would make
  strip geometry, legend row count, and the contrast-gate arity vary per ramp for no product gain.

**Ramp families** `[ASSUMED — Claude's discretion]`: `Blues`, `Reds`, `Greens`, `Purples`, `Greys`
— the roadmap's stated set plus a neutral. **Exact hex sets are `04-01` plan-time work** under
these binding constraints, which the plan must gate rather than assert by eye:

1. Canonical uppercase `#RRGGBB` — `normalizeColor` returns that form and the legend dedupes on it;
   a lowercase shade would dedupe as a second entry.
2. **Strictly monotone decreasing relative luminance** across the declared order (light → dark),
   asserted step-by-step, RED-proved by swapping steps 1 and 3 via **scratchpad copy-back**.
3. **Globally disjoint shade sets.** `normalizeLegendEntries` rejects a duplicate colour outright,
   so two ramps sharing a hex collapses their legend entries. Assert disjointness in the same unit
   gate. *(This is `04-RESEARCH.md` Open Question 5 — this spec closes it in favour of disjointness,
   because re-keying legend entries off `{rampId, index}` is a storage change for a problem a
   palette choice can avoid.)*
4. **`max(contrast(shade, '#FFFFFF'), contrast(shade, '#111827')) ≥ 4.5`** for every shade.
5. **Do NOT gate 3:1 between adjacent steps.** A 5-step sequential ramp cannot hold 3:1 between
   every neighbour inside sRGB for most hues; the gate would be red on arrival and would then get
   loosened rather than obeyed. **Record adjacent-step separation as a measurement in the plan, not
   as a threshold.** Distinguishability is the legend's job, not the ramp's.

**Contrast math must be extracted, not copied.** `relativeLuminance` / `contrastRatio` exist today
**private to `uiContract.test.ts:266-296`**. Extract them to `src/utils/contrast.ts` with their own
unit test and have **both** `uiContract.test.ts` and the ramp gate import it. Two copies of
luminance math is exactly the drift the `LEGEND_CHARACTERS_PER_LINE` / `LABEL_CHARACTERS_PER_LINE`
duplication already cost this project.

### 6.5 Composition layer stack — what actually reaches the PNG

`isPreservedComposition` compares only the **indices** of the camera and legend children and their
`transform` attributes, so **adding sibling layers is structurally permitted** as long as camera
still precedes legend.

```
svg.map-canvas  (viewBox "0 0 1080 1080")
├── style                            ← injected @font-face(s), FIRST child (existing)
├── rect[data-layer="surface"]       ← NEW  water; x=0 y=0 w=1080 h=1080; inline fill; OUTSIDE camera
├── defs[data-layer="paint"]         ← NEW  band gradients
├── g[data-layer="camera"]           ← existing, MUST stay before the legend
│   ├── g[data-layer="outgoing-scenes"]
│   ├── g[data-layer="countries"]
│   ├── g[data-layer="borders"]      ← NEW  interior mesh; non-interactive; INSIDE camera
│   └── g[data-layer="highlight"]    ← NEW  data-editor-only; hover/selection; INSIDE camera
├── g[data-layer="bands"]            ← NEW  top/bottom gradient rects; OUTSIDE camera
├── g[data-layer="legend"]           ← existing
└── g[data-layer="text"]             ← NEW  title/subtitle/attribution; OUTSIDE camera
```

Three constraints, each verified this session:

1. **Gradient `id`s must be *referenced*.** `sanitizeExportClone` strips `id` unless
   `collectReferencedIds` found a `url(#…)` or `href="#…"` pointing at it. A gradient referenced by
   `fill="url(#band-top)"` is safe; one referenced only from an external stylesheet is not — the id
   is stripped and the gradient silently disappears.
2. **Editor-only affordances carry `data-editor-only`** (band drag handles, text bounding boxes,
   the highlight layer). The sanitizer removes them wholesale.
3. **Bands, text, and legend sit OUTSIDE `[data-layer="camera"]`** or they pan and zoom with the
   map. The legend is the working precedent.

**Paint order, top to bottom** `[ASSUMED — Claude's discretion, band/legend z-order]`:
surface → countries → mesh → highlight → **bands** → **legend** → **text**.
Bands paint *before* legend and text, so the band is a backdrop for type rather than a veil over
it. Gate it with a pixel sample at a deliberate overlap.

**Techniques that are measured-safe and may be specified freely:** `<linearGradient>` with
`stop-opacity`, `<radialGradient>`, gradients defined inside a transformed group, `<clipPath>`,
`<mask>`, `<use>`, `fill-opacity`, `vector-effect` as an **attribute**, `<text>` with
`text-anchor` / `dominant-baseline` / `<tspan>` / `paint-order`.

**Techniques that are forbidden on exported content** (`Design.md § 8`, `EXPORT_UNSAFE_PROPERTIES`):
`filter`, `box-shadow`, `text-shadow`, `mix-blend-mode`, `mask`, `clip-path` **applied from a
stylesheet**; `backdrop-filter` **anywhere**. *Research measured that an **inline** `filter` does
rasterise in Chrome 151 — so the ban's stated reason ("renders not at all") is precise about
external CSS and would be an over-claim about inline styles. **The contract still governs. Do not
use a filter for bands.** SVG gradients are both compliant and measured-safe. This is recorded so
nobody rediscovers the inline case and treats the whole rule as unsound.*

| Position | Title and subtitle live in the **top band**; attribution in the **bottom band**, or at the bottom edge inset `TEXT_SAFE_INSET` when the bottom band is off |
| Sanitisation | Input is sanitised before it reaches the composition. Control characters stripped; the value is written as SVG **text content**, never as markup |

**Font stack: Inter only** `[ASSUMED — Claude's discretion per CONTEXT]`. It is already vendored,
already registered in `EXPORT_FONT_FACE_BUILDERS`, already what the legend names, and its bytes are
already SHA-256-recorded. A second family means a second woff2, a second licence record, a second
README row, and ≈ +65 KB in the serialised SVG. **Adding a display face is a real design decision
the owner has not made — do not make it inside a plan.**

> ⚠ **A named family the registry does not know renders as fallback, silently.**
> `collectCompositionFonts` would report the family, `injectExportFontFace` would find no builder,
> and the export would fall back with **no error**. **If a font picker ever ships, its option list
> must be derived from `EXPORT_FONT_FACE_BUILDERS.keys()`, never from a separate list.**

**latin-ext (D4-15): always inline, never conditionally** `[ASSUMED — Claude's discretion; research
recommended the same]`. `src/utils/export.ts` is the most safety-critical file in the repo, and a
content-dependent branch there trades determinism for a saving that **does not affect output size**
— the base64 font inlines into the **intermediate SVG**, not the PNG raster. Cost is export time and
memory (≈ +113 KB of SVG), not file size. The Phase 3-era "+113 KB per export" framing was about
the wrong artifact and is corrected here.

Ship as **two `@font-face` rules for one family with `unicode-range`** — measured to parse and
render correctly through the export path, so no `fontTools` / `pyftsubset` / `woff2_compress`
toolchain is needed (none is installed). Re-record the SHA-256 in `src/assets/README.md` and
re-verify the OFL-1.1 licence and byte sizes **by live fetch** — the README's numbers are a Phase 3
measurement, not a current one.

### 6.9 Interaction state when there is no coastline to weight

`src/constants/colors.ts` documents that **border weight, not colour, carries interaction state** —
borders are black at every state and hover/selection differentiate by stroke width. With
`coastlineWeight: none` as the default, **there is no coastline stroke left to thicken.**
`04-CONTEXT.md` flags this as *"Unresolved; name it in `04-05`."* **This spec names it.**

> **Contract: hover and selection render on a dedicated `g[data-layer="highlight"]` layer carrying
> `data-editor-only="true"`, completely independent of the composition's coastline weight.**

| Property | Value |
|---|---|
| Contents | One `<path>` per hovered/selected country, cloned geometry, **not** all 207 |
| Fill | `none` |
| Stroke | `--map-border-hover` / `--map-border-selected` (`#000000`) written inline; hover **1.5**, selected **2.5** user units, `vector-effect="non-scaling-stroke"` as an attribute |
| Position | Inside `[data-layer="camera"]`, above `[data-layer="borders"]` |
| Pointer events | `none` — it must never intercept the click it is drawing feedback for |
| Export | **Guaranteed absent.** `sanitizeExportClone` removes `data-editor-only` elements wholesale |

Three reasons this is the right answer rather than a workaround:

1. Interaction state **must never reach the PNG anyway** — the sanitizer already strips `focused`
   and `data-focused` for exactly this reason. A dedicated editor-only layer makes that structural
   instead of incidental.
2. It **decouples** the creator's coastline choice from feedback legibility. Choosing `none` no
   longer costs the creator their hover affordance.
3. It is **RED-provable on its own subject**: select a country, export, assert no selection stroke
   in the PNG; then delete the `data-editor-only` attribute and watch the assertion go red.

> ⚠ **New contract disagreement (CD-11, mine).** `ROADMAP.md § Phase 4 04-05` says weight states
> *"[are] re-expressed on it [the interior mesh]"*. **That is not achievable.** The mesh is a shared
> line layer — each segment belongs to *two* countries — so it cannot express per-country hover or
> selection. The roadmap line needs amendment. **Reported, not resolved.**

## 7. Dark Theme

**The mount root's `.dark` class flips chrome tokens. It must not flip anything that reaches the
PNG.** Phase 4 makes this easier by construction, not harder: composition appearance is now
**persisted creator state written inline**, so it is theme-independent because the theme has no
route to it at all — not because a rule forbids it.

| Surface | Dark behaviour |
|---|---|
| Colors panel, `Map style` panel, ramp pills | Flip with `--themely-*` tokens. **No per-component dark override may be authored** — a component reaching for a dark literal is the start of a second palette |
| Ramp strip segments | **Do NOT flip.** The shades are the product; a shade is not a token |
| Ramp step check glyph | Picks `#FFFFFF` or `#111827` by contrast against the shade — **the same choice in both modes**, because the shade does not change |
| Ramp strip outer border | `--swatch-border` `#9ca3af`, **mode-invariant**, exactly like the swatch borders it rhymes with |
| Map canvas gutter | `--map-surface` `#ffffff` in both modes (mode-invariant, § 5.3) |
| Everything inside the export frame | **Mode-invariant by construction** — inline attributes from composition state |

⚠ **`Design.md § 3`'s mode-invariant table gains no new rows in Phase 4, and must not.** If a plan
finds itself wanting a new fixed token for composition appearance, that is the signal it is about
to paint exported pixels from CSS — which does not work.
