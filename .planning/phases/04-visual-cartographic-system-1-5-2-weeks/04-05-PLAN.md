<objective>
Change what "a country's colour assignment" **is**: from a hex string to `{rampId, t}`, with raw hex
demoted to one variant of the same union, and with **one** `resolveColorValue` chokepoint that every
consumer goes through.

Purpose: D4-02 exists because this is *already* the exact representation Phase 5's CSV engine will
produce — the data path computes `t` from a value instead of from a click — and because switching
ramps can then re-skin every painted country instantly. Getting the identity model wrong here is
expensive later: Phase 5's classing engine is specified against it.

`04-RESEARCH.md § D4-02's blast radius` measured the cost so this plan can be sized honestly. Six
sites assume `string` today: `normalizeColorMap`, `getEffectiveCountryColor`, the
`canonicalizeColorMap` / `applyColorToCountries` / `areColorMapsEqual` / `hasEffectiveColorChange`
family, `getEffectiveSceneColors` feeding `reconcileLegend` (whose entries are keyed and **deduped by
hex**), the undo/redo `ColorHistory`, and `isPresetColor`.

Output: a discriminated `ColorMap` value type, a single resolution chokepoint, six migrated call
sites, and an invariant test that reddens if the hex-only assumption comes back.
</objective>

<assumption_delta_decision>
**The noun:** *a country's colour assignment* — what `ColorMap[countryId]` holds.

**Decision: `promote`.**

`{rampId, t}` becomes the **primary** representation of a colour assignment. Raw hex is **demoted to
one variant** of the same discriminated union — the *custom* variant — rather than remaining a
co-equal parallel model. `resolveColorValue` is the single reader that turns either variant into a
hex, exactly as `resolveLegendPosition` is the only reader of `legend.position` under Live
Invariant 3.

**Rationale.** `04-CONTEXT.md` is explicit that "a painted country stores `{rampId, t}` rather than
hex, so Phase 5's CSV drives the identical pipeline". That is a generalization, and the correct move
on a generalization is to promote the general representation and demote the specific one — **not** to
add the new one alongside the still-required old one. Adding alongside is precisely research option
(B) (a separate `rampAssignments` map with `ColorMap` still holding resolved hex), which
`04-RESEARCH.md` rejects because it creates **two sources of truth that can disagree** — the exact
drift hazard `coding-rules/general.md` names — and because it contradicts the letter of D4-02 ("hex is
resolved at render time").

**Not `add-alongside`, and therefore no accepted debt is recorded here.** If Task 1's owner gate
selects option (B) instead, the executor **must** rewrite this block to `add-alongside`, name it as
accepted debt, and state what would force a later promote — which would be Phase 5's classing engine
needing a ramp identity that `ColorMap` does not carry.

**Invariant test (suggested, and this plan lands it):** Task 3 adds an assertion that a
ramp-assignment value survives a full round trip — apply, canonicalise, snapshot into history, undo,
redo — **still as a ramp assignment**, never having degraded to a hex. That assertion goes red the
instant a future phase reintroduces the hex-only assumption anywhere on that path. Phase 5's CSV
import binds to exactly this, so the assertion is cheap insurance against an expensive regression.
</assumption_delta_decision>
