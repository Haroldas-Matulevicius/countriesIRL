**`Move Map` is retained deliberately.** D-21 names three controls; this is a fourth, kept because
the pan popover is the **only keyboard pan affordance** in the app and dropping it would regress
NFR11 and the keyboard-navigation acceptance cells. It was flagged for owner awareness in
`03-UI-SPEC.md` § Open Items item 2 rather than decided silently. If the owner later wants a
three-control cluster, keyboard panning needs a replacement **first**. Record this in the SUMMARY
as a retained-by-decision item, not as an accident.

**B. Re-anchor into the letterbox gutter.** Use the container math from the UI-SPEC verbatim:

`--frame-side: min(100cqw, 100cqh)`;
`inset-inline-end: max(var(--space-lg), calc((100cqw - var(--frame-side)) / 2 + var(--space-sm)))`;
`inset-block-end: max(var(--space-lg), calc((100cqh - var(--frame-side)) / 2 + var(--space-sm)))`.

Pure CSS container math — **no measurement, no `ResizeObserver`**. Because `--frame-side` is
`min(w, h)`, at least one gutter is non-zero at any non-square canvas region and the cluster is
pushed clear on that axis.

**The bounded exception is documented, not hidden.** When the canvas region is within ~96px of
square, neither gutter fits and the cluster rests over the frame's bottom-right corner. Accepted
because (a) it is editor-only chrome that never enters the PNG, (b) the wrapper is
`pointer-events: none` with `auto` restored only on the four button rects, and (c) the legend's
default preset is top-left. Write that reason into the stylesheet as a comment on the rule.

**C. Retire the two shadow consumers.** `MapCanvas.css:216` and `:250` consume
`--shadow-navigation`, deleted in 03-04. They consume `--popover-shadow` now. The
`--glass-navigation` consumer at `:214` and its blur at `:221` are gone with the family;
`backdrop-filter` is banned outright.

**D. Assertion 12 — non-intersection, not placement.** In `tests/e2e/navigation.spec.ts`, assert
the cluster's client rect does **not intersect** `.map-frame`'s client rect at every spec'd
viewport **and at every legend preset**. Asserting a *position* would pass against a cluster that
happens to sit somewhere harmless; asserting **non-intersection** is what goes RED when a
regression re-anchors it into the frame at a normal viewport.

Enumerate the legend presets from `resolveLegendRender` rather than hard-coding them, so a new
preset is covered automatically.

Carry D-23 forward verbatim and gate it so a regression cannot pass.

**A. Cursor.** A colourable unit gets `cursor: pointer`. A non-colourable unit
(`colorOwnerId === null` — Kosovo, Western Sahara, Antarctica; **12 units**) gets
`cursor: default`. This is the honest signal: the cursor promises an interaction the map can
actually perform.

**B. Fill.** A non-colourable unit keeps `NEUTRAL_UNIT_COLOR`'s **solid light-grey fill in BOTH
colour resolvers**. Both — a single resolver updated leaves the other rendering the unit as
colourable-looking, which is how this surfaced before.

**The neutral fill is a solid colour, never a CSS `filter`.** A `filter` is export-unsafe: under
D-34 the clone is rasterised inside an SVG-as-image isolated document that sees none of the host
page's stylesheets, so an externally-styled effect renders **not at all** — the PNG quietly loses
it while the editor looks correct. Assertion 17 bans it; this is the concrete reason.

**C. Copy.** The tooltip for a non-colourable unit states the honest reason —
`Not colorable in this map` — **rather than announcing a colour**. No "coming soon", no promise of
a future capability, no colour readout.

**D. The gate, and it must be able to fail on the bug it covers.** Roadmap `03-08` requires an
assertion that goes RED if this regresses to a colour readout. In `tests/e2e/navigation.spec.ts`,
assert for at least one unit of each kind:
- a colourable unit resolves `cursor: pointer` and its tooltip shows a colour readout;
- a non-colourable unit resolves `cursor: default`, renders the neutral grey fill, and its
  tooltip carries the honest reason and **no colour readout**.

Assert the **negative** explicitly — the absence of a colour readout — not just the presence of
the reason string. A tooltip that shows both would pass a presence-only check.

*RED probe (mandatory task step):* copy the tooltip content builder to the scratchpad, make the

`npx playwright test tests/e2e/navigation.spec.ts --project=chrome`, OBSERVE RED, capture output,
restore by copying back, re-run green. Run a second probe on the cursor: give the non-colourable

**E. Do not change which units are non-colourable.** The set is data-derived from `colorOwnerId`.
This plan restyles and gates; it does not re-classify a unit. A change to the classification is a
data decision, not chrome.
