would silently drop an accessibility guarantee.

**C. Delete only what is genuinely unreachable.** A class still referenced by a component, a unit
test locator, or an e2e selector is **not dead**, however unused it looks. Before deleting a rule,
grep for its class across `src/` and `tests/`. Record in the SUMMARY the count of rules deleted and
the count merely moved — those are different claims and conflating them overstates the sweep.

**D. Update `main.tsx`'s import list** to match the new file set exactly. The parser constraint
matters here: 03-03 already changed the contract test to **glob** `src/styles/**/*.css` rather than
hard-code four filenames, precisely so a new file cannot silently escape every assertion. Task 2
turns the glob-vs-import equality into assertion 20.

**E. Comment density matched to the new files.** Each new file gets a short header saying what
surface it owns. **Do not paste the old file's block comments across wholesale**, and — this is a
hard rule — **do not write into any comment a literal that a contract assertion negative-greps
for.** A header comment naming a forbidden token or a forbidden at-rule makes the gate
self-invalidating, and this repo has already shipped gates that could not fail. Where a count is
taken over a stylesheet, comment lines are stripped first.

**F. Prove no visual or behavioural change.** This is a move, not a redesign. Run the full Chrome
e2e suite after the split and confirm it is green. A rule that changed behaviour when moved was
order-dependent, and that dependency must be recorded, not silently preserved by luck.

  <action>
Land assertion 21: **the distinct-selector inventory is AT MOST a recorded count, so growth
fails.**

The roadmap words the `03-10` gate as *"contract test's selector inventory shrinks — asserted, so
growth fails."* Implement it as a ceiling rather than an exact match: an exact match forces a test
edit on every legitimate deletion and trains people to bump the number reflexively. A ceiling
fails only on growth, which is the behaviour worth catching.

Measure the count **after** the sweep and record it as the ceiling, with the pre-sweep count
recorded beside it in the SUMMARY so the shrink is a stated number rather than an impression.

**Count selectors, not lines, and strip comments first.** `grep -c` over a raw stylesheet counts
comment text; a header comment mentioning a class name would inflate the count and, worse, a
comment mentioning a *forbidden* token would satisfy or defeat a neighbouring negative gate. The
parser already tokenises rules — use it rather than a raw text count.

**Record the maintenance rule in `.planning/coding-rules/frontend.md` in this same commit**
(documentation-as-you-build): the ceiling is lowered when rules are deleted and may only be raised
with a stated reason in the commit that raises it. Bump its `Last updated` line and keep at most
**two** entries — merge the two oldest into one line in the same edit if a third would appear.
`frontend.md` had accumulated seven before.

*RED probe (mandatory task step):* add a dead rule to any stylesheet, run
`npx vitest run src/styles/uiContract.test.ts`, OBSERVE RED, capture output, restore by copying
from the scratchpad, re-run green.
